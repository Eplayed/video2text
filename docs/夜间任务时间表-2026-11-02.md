# 夜间任务时间表与问题优先级（2026-11-02 号主拍板「照这个排程执行」）

号主的要求：**抓取数据 + 自动转写放到后半夜**，并把各任务时刻排合理。
下面是当时的问题优先级与方案；**执行状态见文末第 4 节**（有一处按现场证据改了做法）。

## 0. 一条前置硬条件（不成立的话，整个后半夜方案是假的）

- 现在机器整夜没睡，**不是配了唤醒**，是网易 UU 远程一直持有
  `PreventUserIdleSystemSleep`（实测已连顶 19 小时 59 分）。旁证：`we-mp-rss` 容器
  在 00:00–06:00 每小时仍有 7 条日志，说明宿主机整夜在跑。
- 而系统设置是 **AC 电源下 `sleep 1`**（空闲 1 分钟就休眠）、`womp 0`（网卡不唤醒）、
  `pmset -g sched` 空（没有任何定时唤醒）。
- 结论：**他哪天关掉远程工具，后半夜所有任务会静默不跑，而且不会报错**——
  这正是 10-30 那份清单里"没开就不跑"的那条病，只是换了触发方式。
- 方案（要 sudo，我不擅自跑）：
  ```
  sudo pmset repeat wakeorpoweron MTWRFSU 01:45:00
  sudo pmset -c sleep 0 disksleep 0       # 只插着电时不休眠（合盖/拔电不受影响）
  ```
  二选一就够；`wakeorpoweron` 改动小、可回退（`sudo pmset repeat cancel`）。

## 2. 建议时刻表（后半夜版）

| 时刻 | 任务 | 为什么是这个点 |
|---|---|---|
| 01:45 | 定时唤醒（`pmset`，前置） | 给后面三档留出"机器确实醒着"的余量 |
| **02:00** | 订阅抓取：抖音 + 魔兽（含 B 站投稿列表） | 抓取不吃 CPU、不花钱，先跑完才能喂转写 |
| **02:20** | B 站自动链：本地转写 → 抽关键帧（按号排队，跑完这轮才走下一个号） | 实测 4.5× 实时；一晚 40–60 条约 60–90 分钟，02:20 起最迟 04:00 收工，全在他睡觉时 |
| 04:30 | 微信 6 个号 | 上游 `we-mp-rss` 全天在刷（实测每小时都有任务完成），夜里跑能吃掉凌晨发的文章；"全文未就绪"那批到早上也已被上游补过一轮 |
| 05:00 | NGA 快照导入（吃前一天 **20:40** 那份）+ 暴雪官方公告 | 现在要等到 10:40 才进库；夜里进，早上写稿就查得到 |
| 06:30 | 排产匹配（原 22:00 那一档挪过来） | **必须排在抓取/转写之后**，否则又是"早上看到的表比素材库旧一天"。3 秒跑完 |
| 09:05 | NGA 快照导入第二次（吃当天 **08:40** 那份） | NGA 采集 08:40/20:40 在 wow-forever 那条线（别人的 launchd，我不动时刻）；本仓库加一档幂等导入，白天那份就不必等明天 |
| **18:30** | 补抓一次（只抓不转写） | 魔兽号常在傍晚发新稿；这轮把料攒进队列，**转写统一留给下一夜 02:20**，白天不跟他抢 CPU |

三条设计原则，改动时别破：
1. **吃 CPU 的都排在夜里**（whisper、抽帧前的下载），便宜的（抓列表、拉 RSS）可以一天两档；
2. **匹配永远排在抓取与转写之后**——这是这次"表不动"的真正病根；
3. 时刻都存配置（`config/sync_tasks.json` 每任务一份、`config/plan_match.json` 一档），
   界面「数据与同步」能改，不写死在代码里。

## 3. 落地顺序（他点头后我按这个跑）

1. `pmset` 定时唤醒（要他输 sudo 密码或他自己贴命令）；
2. 改时刻：抓取 02:00 / 微信 04:30 / NGA+暴雪 05:00 / 匹配 06:30 + 新增 18:30 补抓档
   （都走界面同一套配置，不改判据代码）；
3. 自动链加运行窗口与每日条数上限（`web/app.py` 一个判断 + 回执文案）；
4. 排队状态落盘 + 启动续跑（P1，防止"重启吃掉今天"再发生）；
5. 回归：`e2e_sync_tasks.py`（时刻口径）+ `e2e_bili_pipeline.py`（链与闸）+ `e2e_plan_series.py`，
   再重启工作台，第二天早上用真实日志复核一遍"每档都按点跑了"。

## 4. 09:57 执行结果（当天上午就落了）

回归：`e2e_bili_pipeline.py` 66 条、`e2e_plan_series.py` 176 条、`e2e_sync_tasks.py` 全绿。

**改了一处做法（有证据，不是偷懒）**：NGA 导入不做两档，只留 09:05 一档。
`sync_tasks.new_source_task()` 有意规定同一个源只留一条、`_nga_task()` 也只认第一条命中，
手搓第二条要破这条既有规矩；而 NGA 是**非视频补充料**，进不了候选，
`sup_n` 是看板读的时候现算的，与匹配时机无关 —— 05:00 那档没有收益。
代价：前一天 20:40 那份快照要等次日 09:05 才进库（今天实测 09:57 那次补跑就吃了当天 08:40 的 72 条）。

**还剩的一件**：
1. P1 里的"重启丢作业"只解决了排队那一半（队列落盘 + 启动续跑）；
   **正在跑的那趟作业被重启杀掉仍然会从头再来**（素材没正文=天然幂等，重跑不花钱，但那一晚的额度白费）。
   要不要给作业加"分段 checkpoint"，等哪天真撞上再说。

明天该复核的（早上看一眼就行）：02:00 抓取是否按点、02:20 那趟自动链是否跑完并落在窗口内、
06:30 匹配是否第一次自己跑、18:30 那档是否只攒不跑（回执应写"不在窗口内，留在队列里等夜里"）。

（`pmset` 那条号主当天就配了，`pmset -g sched` 实测回读：`wakepoweron at 1:45AM every day`。）

## 5. 12:5x 追加：让"每天都更新"真的成立（号主看完表之后提的那一句）

上面那套时刻表只解决了"匹配排在抓取之后"，还差三件，都在这单元落了（判据与理由见
`CHANGELOG_FOR_AI.md` 的 11-02 第三单）：

| 加的东西 | 一句话 | 实测 |
|---|---|---|
| 补刷一轮 | `videos` 最新 `updated_at` 晚于上一次成功那轮 → 再刷一轮（每小时最多一轮，0 元、不采用不发布） | 重启后 35 秒自己起了一轮：`fresh:2026-11-02:124710`，新增 36 条候选 |
| 啃积压 | 当天没抓到新料的号也排得上：额度先给新料，剩下按"积压最年轻"分；05:30 起那一眼兜底，一晚只一轮，给新料留 40 条 | 现状积压：好赛雷切片 324 条（≤45 分钟）、神奇海挪 40、漫步魔兽 1 |
| 贴题档 | 候选排序 `Forever 确定 → 命中词数 → 日期新 → 正文长`，命中数存进 `plan_candidates.nk`，看板读的顺序同一档判据 | 42 格里 40 格候选超上限；改成贴题档要换掉 212 条候选 |

且改成**跨作业累计**（`config/bili_chain_state.json` 里 `night`+`spent`+`drain_on` 三个键）。
